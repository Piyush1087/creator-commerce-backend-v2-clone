Based on your description of the workflow and the highly complex Brand Centre document you shared, your intuition about where things went wrong is spot on. Building a complex platform using a chain of AI tools (Gemini for PRD/Zod $\\rightarrow$ Stitch for UI $\\rightarrow$ AntiGravity/Cursor for backend integration) is incredibly efficient, but it creates "translation loss" at each handoff point.  
Here is an expanded analysis of the possible reasons for the gaps, directly referencing the architecture of your product:

### **1\. AI Integration & LLM Hallucinations (Expanding on Reason 8\)**

Your application relies heavily on asynchronous AI processing (Events 2 and 3\) to generate data.

* **Strict Constraints vs. LLM Variability:** Your system prompt mandates strict mathematical and structural constraints, such as ensuring budget distributions (like assetMix, tierMix) sum to exactly 100 , and the "Power of 3" rule, which strictly limits the generation of Core Brand USPs to exactly three (3) distinct items. LLMs notoriously struggle with strict mathematical counting. If the AI returns 4 USPs or percentages that sum to 99%, your Zod validation schemas will instantly reject the payload, resulting in missing data, silent failures, or blank screens on the frontend.  
* **Timeout Issues:** Generating comprehensive Tab 1 and Tab 2 baselines via LLMs can take 15–30 seconds. If your AWS API Gateway or Lambda functions have standard timeouts (e.g., 10 seconds), the AI responses are likely being cut off before they reach the frontend.

### **2\. Complex UI State Translation Loss (Expanding on Reasons 2, 3, & 5\)**

Stitch is great for static UI, but your platform has highly complex interactive states that likely broke when imported into AntiGravity/Cursor:

* **Interconnected Sliders:** The PRD specifies that modifying one financial slider shifts the remaining sliders dynamically within that row, and the aggregate percentage of any cluster must sum up to exactly 100%. This requires complex useState or useReducer hooks in React. A UI generator like Stitch will almost certainly miss this dynamic interconnected logic, and the developer might not have fully recreated the math in the frontend code.  
* **Sticky Drawers & Z-Index Conflicts:** The platform heavily features sliding drawers and overlays. Automated UI generation often struggles with portal mounting and z-index contexts. When the developer connected these, states like the "Sticky Footer Constraint" or the mobile bottom-sheet overlays might be clashing, rendering action buttons unclickable or invisible.

### **3\. Backend & Database Sync Mismatches (Expanding on Reasons 4, 6, & 7\)**

* **Zod vs. Database Trigger Conflicts:** You used Gemini to create both PostgreSQL schemas and Zod schemas. However, your document mentions complex backend rules, such as a database-level BEFORE UPDATE row trigger to limit budget edits. If this triggers in PostgreSQL, it throws a SQL execution error. If the developer didn't map this specific database error to a friendly frontend state, the application will simply crash or show a generic "Runtime Error" to the user.  
* **Asynchronous Race Conditions:** Your architecture features a synchronous Event 1 (Cold Start) and an asynchronous Event 2 (Post-Email Webhook). If the frontend attempts to render Tab 2 (Intelligence & Gaps) before Event 2 finishes saving the AI-generated data to AWS, the app will try to read null data, causing immediate frontend crashes.

### **4\. Edge Cases in Business Logic (Expanding on Reason 1\)**

* **The "Circuit Breaker" Logic:** You have complex conditional math, like the Budget Overload Circuit Breaker which halts campaign execution if liabilities exceed the budget float. If this logic was only documented in the PRD but not strictly unit-tested during the AntiGravity/Cursor integration phase, unexpected float numbers (like missing decimals or string-to-number conversion errors) will break the execution flow.  
* **Mobile Breakpoint Logic:** The PRD specifies converting the navigation into a horizontally scrollable text ribbon with hidden native scrolltracks below 768px. Mobile touch-events and scroll-snapping are notoriously difficult to perfect via automated UI tools and require manual developer tuning to ensure they don't break the user experience.

### **Next Steps to Fix the Gaps**

To stabilize the platform, I recommend having your developer look into three specific areas:

1. **Implement Fallbacks for AI Prompts:** Wrap the Gemini backend calls in retry loops. If the AI returns 99% instead of 100%, write a backend script that automatically normalizes the data before it hits the Zod validation layer.  
2. **Audit Error Boundaries:** Ensure your frontend has React Error Boundaries (or similar) so that when a Zod validation fails, the user sees a graceful error ("AI is recalculating...") rather than a broken page.  
3. **Check AWS Logs (CloudWatch):** Look for "Timeout" errors or "Out of Memory" errors on the AI Webhook functions to rule out infrastructure as the cause for missing frontend data.

# Functional document structure

To create an automated or developer-driven functional document reverse-engineered directly from your backend and frontend code, you need a **Living Functional Specification (LFS)** framework. Unlike a traditional PRD, which states what the product *should* do, this document structures what the code *actually* does.  
To make this document highly actionable, it should explicitly tie every single business rule to its exact **Technical Point of Impact** in your stack.

### **The 6 Key Technical Points of Impact**

When code is analyzed to build this document, every use case or validation rule manifests in one or more of these layers. The document must map each rule to its corresponding point of impact:

1. **Database Layer (PostgreSQL Schema):** Defines hard structural truths. (e.g., NOT NULL constraints, UNIQUE indexes, Foreign Keys, data types like NUMERIC(10,2), and DB triggers).  
2. **Runtime Validation Layer (Zod Schemas):** Catches data corruption at the API gateway before it hits the database or the UI. (e.g., .refine() methods checking mathematical equations, .min(3).max(3) string or array lengths).  
3. **Application & Business Logic Layer (Node/Express/Next.js Backend):** Complex procedural calculations. (e.g., currency conversions, conditional branching, circuit breakers that prevent campaign execution if float limits are breached).  
4. **AI/LLM Prompt Layer (System Prompts & Prompt Templates):** Cognitive constraints enforced via the backend. (e.g., instructing Gemini to format responses in a specific JSON shape, or enforcing the "Power of 3" rule via prompt engineering).  
5. **Frontend State & Interaction Layer (React Hooks/Context):** UI behavior during active user inputs. (e.g., adjusting slider rows dynamically so they always sum up to 100% in real-time).  
6. **Frontend View & Visual Layer (Tailwind/CSS & React Components):** Display states and layout rules. (e.g., viewport media queries changing navigation menus, loading indicators for async webhooks, and Error Boundary wrappers).
